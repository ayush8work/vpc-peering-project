Project overview

Build a routed private link — then prove every path

01
🏗️

Segmented network design

VPC A contains a public and a private subnet; VPC B contains only a private subnet. Only the bastion receives a public IPv4 — application hosts stay unreachable from the internet.

02
🔗

VPC peering connection

A pcx- connection links VPC A and VPC B directly. Peering itself is only a link — it carries no routes, so the forwarding decision lives entirely in each VPC's route tables.

03
🛣️

Symmetric routing

Route tables on both sides are configured with the peer CIDR. Without the return route in VPC B, replies never find their way home — validated by a fail-first baseline ping.

04
🔐

Bastion-only SSH access

A single key pair and SSH ProxyJump gives access to both private hosts through the bastion. Security groups authorise SSH from exactly one private source IP: 10.10.1.10/32.

05
🛡️

Stateful enforcement

ICMP echo between the applications is permitted only between the two app IPs (/32). Removing that single rule blocks traffic even with peering active — policy outlives topology.

06
🧹

Tagged, reversible build

Every resource is tagged Project=vpc-peering; automation creates the stack in one run and tears it down to zero, verified by tag-filtered queries.

Under the hood

How the private path comes together

1️⃣

The link

create-vpc-peering-connection from VPC A, accepted from VPC B. Both VPC IDs and the pcx- connection must be Active — but no traffic moves yet.

2️⃣

The forward route

A's route tables (public and private) receive 10.20.0.0/16 → pcx…. Now packets from app-a toward 10.20.1.10 leave VPC A through the peering edge.

3️⃣

The return route

B's route table receives 10.10.0.0/16 → pcx…. Replies are routed back — without this, the forward ping transmits but never completes. This is routing symmetry.

4️⃣

The policy gate

vpc-peering-app-b allows ICMP echo only from 10.10.2.10/32 and SSH only from 10.10.1.10/32 (the bastion's source as used by ProxyJump). Policy decides on top of routing.

Conclusion

What this project establishes

Peering is a link, not connectivity

An Active peering connection only joins two VPCs. Actual reachability required three distinct pieces: the peering connection, the forward route in VPC A, and the return route in VPC B. The baseline test isolated exactly which piece was missing at each stage.

Security travels in the right layer

Routing and policy are independently changeable. The controlled test removed a single ICMP authorisation while routing stayed intact — traffic stopped; restoring it restored service. Network topology gives the path; security groups decide who may walk it.

Private hosts stay private

SSH reaches both app hosts through one public entry point using ProxyJump, and even then the reused source IP is the bastion's private address — the security model never depends on the operator's location.

Build reproducibility

The whole network is expressed as tagged CLI automation with a clean teardown path: create in one run, validate in a scripted test matrix, destroy to zero and verify — repeatable on any AWS account and region.
